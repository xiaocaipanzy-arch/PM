# 历史迭代侧重点与原型关系

依据：源表57条记录、34条蓝湖链接，以及项目35份RP/199个节点。以下是材料归纳，不是业务效果验证。源表没有版本日期，使用记录顺序。

## 整体方向
投入重点呈现为：商家供给与基础链路 → 履约可靠性和规则 → 商家经营效率与数据 → 支付和订单基础设施 → 可配置运营增长。各方向交错推进，不能当作严格按时间切分的六个阶段。

### #1—#6 商家供给与基础链路
先建立商家入驻、上传审核、账号配置和前后台配套，再补资金与合规告知。
从平台自有供给向商家可经营的供给体系扩展。

### #7—#23 履约可靠性与规则约束
退款、上号失败、Steam版本、封禁检测、共享需知、登录和到期提示持续补齐。
把可下单推进到可履约、可解释、可限制异常。

### #24—#39 经营效率、数据与观测
包时段、收藏、账号经营数据、换绑、MaFile上传、排序与搜索同时推进；风控开始关联订单和比赛。
提升商家经营效率与用户找号效率，并加强过程可观测性。

### #40—#46 支付与订单基础设施
易宝并行接入、补丁和去除富友构成一条连续支付迁移线，伴随订单、共享规则、锁单和开关细化。
把支付、资金和订单控制做成持续演进的基础能力。

### #47—#56 可配置的运营增长
优惠券从基础发放发展到CDK领取、长线配置与自动选券，并与定价、价格展示和帮助内容配置配合。
从一次性活动走向可复用、可约束的运营工具；履约修补仍在并行。

### #57 0元租的全链路规划
原型覆盖用户资格、专区、订单兼容、后台号池、规则、补贴和商家订单。源表状态仍为规划中。
增长能力继续向分群触达、供给池和预算控制延伸，不能据原型存在推定已上线。

## 具体例子
- 商家端一期：P35同时覆盖登录、首页、公告、上传、审核、账号配置与订单；两个钱包页明确标先不做，不能算一期已交付能力。
- 商家端版本-前台补丁：P33包含筛选优化、商品详情、支付逻辑和订单详情；它们是同一条更新记录里的多个关联页面。筛选页里的三种价格卡片又是同一画布中的不同租赁类型示例。
- 提现版本：P32同时描述商家操作和后台审核/资金流水，多个角色页面共同组成一条提现链路，不是多次独立更新。

## RP里的多页与每次更新是什么关系
一条源表记录表示一次被记录的需求/更新；一份RP是与之关联的原型文档。RP内可同时包含前台、后台、商家端、弹窗、状态、规则说明、复用页面、目录及暂缓页。因此，199个页面节点既不表示199次更新，也不能认为RP里的所有页面都在本次修改。
33条链接按文件标识匹配；收藏按相同根页面标识关联现有同名文件，旧文件内容是否一致尚未验证。0元租是项目补充原型，源表仍为规划中。
页名/原注释明确写新增、修改、优化时标记“明示改动”；其余标记“版本关联页，是否本次改动未确认”。只有对比同一RP的前后修订或变更记录后，才能进一步确认具体差异。
